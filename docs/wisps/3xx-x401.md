## Purpose

A bot built on the headless runtime ([1100](1100-headless.md)) calls websites and APIs for its person. Some of them want to know who stands behind the bot before they answer: a licensed professional, an adult, a customer of a given bank. [x401](https://x401.id) is an open protocol for that question over HTTP. The site answers `401` with a proof request; the agent answers with a presentation of a verifiable credential the person holds, showing only the claims asked for (for example "over 18" without the birth date), and may trade it for a short-lived token.

This WISP fixes how a Ghostly profile plays the **agent** and **credential manager** sides of x401: where the credentials live, what the person approves before a bot presents one, which command does it, and how it relates to Ghostly's own identity proofs. Ghostly does not act as a verifier or an issuer, and nothing here goes between Ghostly peers.

## x401 in one page (version 0.2.0)

The [specification](https://x401.proof.com/spec/) is a draft. Ghostly pins one version: **0.2.0**. Every header value is base64url (no padding) of one UTF-8 JSON object.

| Header | From | Carries |
|---|---|---|
| `PROOF-REQUEST` | Verifier, with the protected route's `401` | `scheme: "x401"`, `version`, `credential_requirements` (a `CredentialRequestOptions` whose `digital.requests[]` are OpenID4VP requests, protocol `openid4vp-v1-signed` or `openid4vp-v1-unsigned`), optional `oauth` (`token_endpoint`, `audience`, `resource`), `request_id`, `satisfied_requirements`, `payment` |
| `PROOF-RESPONSE` | Agent, on the retry of the same route | A **Result Artifact** (`credential_result: {protocol, data}` or `credential_result_uri`, optional `expires_at`, `request_id`, `agent_id`), or an **x401 Token Object** (`scheme`, `version`, `token_type: "Bearer"`, `access_token`) |
| `PROOF-RESULT` | Verifier, when a proof failed | An error object: `scheme`, `version`, `error`, optional `error_description`, `error_uri`, `request_id` |

The OpenID4VP request holds the binding (`client_id`, `expected_origins`, `nonce`, `exp`) and a DCQL query: which credential formats and types, which claim paths and values, and the issuers the verifier trusts (`trusted_authorities`, advisory to the agent). With `oauth.token_endpoint`, the agent may POST the Result Artifact there (RFC 8693 token exchange, `subject_token_type=urn:x401:params:oauth:token-type:result_artifact`) and send the `access_token` it gets back as `Authorization: Bearer` on later calls, until it expires.

The specification sets no rule on asking the holder before a presentation; this WISP adds one ([Approval](#approval)).

## Credentials kept per profile

A profile holds its x401 credentials in its own store ([04](04-profiles.md)), under the key `x401Credentials`, beside its identity proofs. Each record:

| Field | Meaning |
|---|---|
| `id` | Random, chosen by Ghostly, shown in the CLI |
| `label` | The person's name for it ("work licence") |
| `format` | `dc+sd-jwt` (SD-JWT VC) in 1.4; `jwt_vc_json` and `mso_mdoc` are later ([Open decisions](#open-decisions)) |
| `credential` | The issued credential as the issuer gave it, with every disclosure |
| `type` | The credential type the DCQL query matches (`vct` for SD-JWT VC) |
| `issuer` | The issuer as the credential names it; shown, never trusted by Ghostly |
| `holderKey` | The private key the credential is bound to (`cnf`), sealed as identity-proof seeds are |
| `addedAt`, `notBefore`, `expiresAt` | When it was added, and the credential's own validity (`nbf`, `exp`) when it has one |

**Holder keys.** SD-JWT VC binds a credential to a key the holder proves it has (a Key Binding JWT). Ghostly's own keys are Ed25519, and issuers mostly expect P-256 (`ES256`). So each credential gets **its own P-256 key**, created by Ghostly before the person asks the issuer for the credential, and used for nothing else. It is not the profile key, a WISP 300 proof key or the profile DID ([310](310-did-dht.md)): one key per credential keeps two verifiers from linking two presentations by the key, and keeps a credential from tying the bot's chats to its web calls.

**At rest.** Records sit in the profile store, whose files are 0600 under a 0700 folder ([1100](1100-headless.md)). The holder key is sealed as an identity proof's seed is: that protects against a copy of one record, not against someone who can read the whole profile folder. A profile backup ([05](05-backups.md)) carries the credentials and keys, encrypted with the backup's passphrase, so a restored bot keeps them.

**Getting one.** In 1.4 the person brings a credential an issuer already gave them: Ghostly prints a fresh holder public key (JWK) for the issuer to bind, then imports the issued credential and checks that its `cnf` is that key, that it parses (every disclosure named by a digest of the credential, SHA-256 only) and that it has not expired. Import makes no network request; the issuer's signature is checked before a presentation, when the issuer's key can be found (`iss` of an SD-JWT VC, its `/.well-known/jwt-vc-issuer`). A key waits for its credential until 8 newer keys were made; a profile keeps at most 32 credentials, and "Clear all data" ([04](04-profiles.md)) deletes them with their keys. Issuance over OpenID4VCI is later.

**Never shared with contacts.** x401 credentials are not identity proofs ([300](300-peer-proofs.md)): they are not offered in chats, not in the public profile, and no contact can ask for them. Nothing in a chat or group starts a presentation.

## Answering a proof request

`ghostly x401 fetch <url>` (one-shot or through the daemon) makes one HTTP request and answers at most one proof request on it:

1. **Call the route.** HTTPS only. Redirects are followed one hop at a time, at most 5, each hop HTTPS and never to a loopback, private or link-local address. No cookies, no ambient credentials, 15 s per hop, the response body capped (16 MiB by default, `--max-bytes`). A test build alone accepts `http://` to loopback, for a local verifier.
2. **Read the request.** A `401` (or any status) with one `PROOF-REQUEST` header is a proof request. More than one such header, a value over 16 KiB, bad base64url, a non-object, `scheme` other than `x401`, or a `version` other than `0.2.0` fail with `refused` and say why; nothing is presented. Unknown members are ignored. The agent MUST NOT change `credential_requirements`.
3. **Pick a request it can answer.** Among `digital.requests`, a signed one (`openid4vp-v1-signed`) is preferred. A signed request is checked: ES256 only, the `client_id` names **the host this command called** (`x509_san_dns:<host>` only; other prefixes are refused), `exp` has not passed, the leaf certificate of `x5c` signed the JAR, and the chain validates to the trusted roots (Node's default store: its bundled roots and `NODE_EXTRA_CA_CERTS`) with a DNS SAN of the leaf being that host (never its common name). A request for another host is refused before its certificate is looked at. A CLI has no browser origin, so the origin it called stands in for one: `expected_origins`, when present, must list that origin. An unsigned request is bound only to that origin and its `nonce` (its Key Binding JWT's `aud` is `origin:<origin>`, and a `client_id` in it is ignored); it can be answered, but only with a fresh approval ([Approval](#approval)). `response_type` must be `vp_token` and `response_mode` `dc_api` or `dc_api.jwt`.
4. **Match the DCQL query** against the profile's credentials valid now (past their `nbf`, before their `exp`): format, type (`vct` / `meta.type_values`), every claim path asked for, and any `values` the query requires. `trusted_authorities` is shown to the person as the verifier's hint; Ghostly never decides from it that the verifier will accept a credential. No match fails with `not_found` and lists what was asked.
5. **Ask, or use a grant** ([Approval](#approval)).
6. **Present.** For SD-JWT VC: the issuer-signed JWT, only the disclosures for the approved claim paths, and a Key Binding JWT signed by the credential's holder key with `aud` = the request's `client_id`, `nonce` = its `nonce`, `iat` = now and `sd_hash` over the presentation. The `vp_token` is keyed by the DCQL credential query id. When the request asks for an encrypted response (`dc_api.jwt`), the result is encrypted to the verifier's key from the request, or the command fails with `refused` if Ghostly cannot.
7. **Retry the same route** with the same method, headers and body plus `PROOF-RESPONSE: <Result Artifact>` (inline `credential_result`, never `credential_result_uri`, which needs a server). One retry only: a second proof request on the retry fails with `refused`. A `PROOF-RESULT` on the answer fails with `refused` and its `error` and `error_description` (shown as the verifier's words, untrusted).
8. **Exchange for a token**, when `oauth.token_endpoint` is present, HTTPS, and the person's approval covered it: POST the token exchange (with `resource` and `audience` when given), keep the `access_token` in the daemon's memory until `expires_in` runs out (one hour at most, five minutes when absent), and send it as `Authorization: Bearer` on later calls to that route's origin and `resource`. When the call already carries an `Authorization` header, the token goes as an x401 Token Object in `PROOF-RESPONSE` instead. A one-shot keeps no token. Tokens never reach the event stream or a log.

The answer is the route's final status, headers and body, plus `x401: {presented, credential, verifier, claims, token}` (`claims` the paths disclosed; `token` whether one is held, never its value).

`--no-proof` makes the call and only reports a proof request (verifier, claims asked, matching credentials), so a bot can show its person what a site wants before anything is approved. `--payment` is not implemented: a `payment` hint is shown, and x402 stays a separate step.

## Approval

The person approves **the verifier, the credential and the exact claims disclosed**, never "x401 in general". What is shown: the verifier (`client_id`, the host called, signed or unsigned), the credential (label, issuer, type), each claim path and the value it would disclose, the token endpoint's host when a token would be fetched, the verifier's issuer hint, and a `payment` hint when present.

A headless bot has no screen, so approval takes three forms:

| Form | How | Covers |
|---|---|---|
| At a terminal | `ghostly x401 fetch` on a TTY asks yes or no before it presents | This request only |
| Approve this request | Without a TTY or a grant, the command fails with `confirm` (exit 5) and `details.approval`: everything above plus a `digest`, SHA-256 over the verifier, each credential id with its claim paths (in any order), and the token endpoint's origin when a token would be fetched. Running it again with `--approve <digest>` presents, if the new request still has that digest | This verifier, credential and claim set, once |
| Standing grant | `ghostly x401 grant add <client_id> <credential> --claims <path,…> [--days n]` (default 30, at most 365), stored under `x401Grants` | Requests from that signed verifier for that credential and **a subset** of those claims, until it expires or is revoked |

A grant never covers an unsigned request, another verifier, another credential, or one claim more than it lists. `x401 grant list` and `x401 grant revoke <id>` manage them; removing a credential removes its grants. The event stream reports `x401.approval` (the same `details.approval`, claim **paths** only, no values) when a request waits, so the bot's program can ask its person through a chat, for example with message buttons ([406](406-message-buttons.md)), and run `--approve` on their yes. As with `confirmReal` ([1100](1100-headless.md)), a program that approves on its own, without the person, is responsible for that. `x401.presented` reports each presentation (verifier, credential id, claim paths, time); `x401 history` lists the last 100.

## Relation to identity proofs and DIDs

| | Identity proofs ([300](300-peer-proofs.md)) | x401 credentials (this WISP) |
|---|---|---|
| Who vouches | The person, by signing with an account or key they control (Nostr, domain, SSH, DID, ...) or a provider attesting a sign-in | A third-party issuer (a government, a bank, a professional body) |
| Shown to | Contacts, in a chat | Websites and APIs, over HTTP |
| Keys | A proof key per proof, Ed25519 | A holder key per credential, P-256 |
| Trust | Each contact checks the proof itself | The verifier decides which issuers it trusts |

A DID ([311](311-did.md)) can be an x401 **agent identifier** (`agent_id`), which the specification leaves optional; 1.4 sends none. Nothing here makes a certified issuer, OpenID Federation or an ETSI trusted list required anywhere in Ghostly, and Ghostly's own proofs stay as they are.

## Commands (planned)

| Command | Does |
|---|---|
| `x401 key new` | A fresh P-256 holder key; prints its public JWK for the issuer. The 8 newest keys wait for a credential: a ninth drops the oldest, and prints its id as `dropped` |
| `x401 credential add <file\|-> [--label …]` | Imports an issued credential bound to a key from `x401 key new`. A key that waits no more is refused with what became of it: it holds another credential (one per key), it was dropped, or it went with a removed credential |
| `x401 credential list`, `x401 credential remove <id>` | This profile's credentials (no claim values unless `--show-secret`); removing one deletes its key and grants |
| `x401 fetch <url> [--method m] [--header k:v]… [--data …\|-] [--approve <digest>] [--no-proof] [--no-token] [--max-bytes n]` | One HTTP call that answers a proof request ([above](#answering-a-proof-request)) |
| `x401 grant add\|list\|revoke`, `x401 history` | Standing grants and past presentations |

Errors use [1100](1100-headless.md)'s codes: `bad_request`, `confirm` (approval needed), `not_found` (no matching credential), `refused` (a request Ghostly will not answer, or the verifier's `PROOF-RESULT`), `timeout`.

## Security and privacy

- **The verifier is who the CLI called.** A signed request must name the host called; a request for another host, an expired one or a bad signature is refused before anything is matched. The Key Binding JWT's `aud` and `nonce` tie a presentation to that verifier and request, so a copy replayed elsewhere fails there.
- **Unsigned requests are weaker.** Anyone on the path who can answer for the host can ask; HTTPS is required, and they never ride a grant.
- **Least disclosure.** Only the disclosures for the approved claim paths leave; a grant names paths, so a verifier that asks for more is asked about again.
- **No server-side fetches on a verifier's word.** `credential_result_uri` and `return_uri` are never used; `token_endpoint` must be HTTPS, is shown at approval, and passes the same address checks as the route.
- **Secrets stay out of logs.** Claim values, credentials, tokens and holder keys never reach the event stream, `daemon.log` or an error's message.
- **Correlation.** One holder key per credential; no `agent_id` in 1.4. A credential with a stable subject still links every verifier it is shown to; the approval says so for claims such as an account or document number.
- **Version drift.** Any `version` other than 0.2.0 is refused; a new version of the specification is a change to this WISP and to the one parsing module.
- **Bounds.** Header and body caps, one retry, at most 5 redirects, 15 s per hop, 64 KiB for an issuer metadata fetch.

## Out of scope

x401 inside chats, groups or apps (a contact or a bot asking another for a proof): the specification is HTTP only, and that would be Ghostly's own extension; it waits for the specification to settle. Acting as a verifier or an issuer. Payments on the same route (x402). The web, Desktop and mobile apps. Agent binding (Web Bot Auth, DPoP, workload identity).

## Open decisions

- **Standing grants or always ask.** Proposed: grants as above, opt-in, signed verifiers only. The alternative asks every time, which a bot that runs unattended cannot use.
- **Formats in 1.4.** Proposed: SD-JWT VC only. `jwt_vc_json` (no selective disclosure) and mdoc (CBOR, ISO 18013-5) follow when a verifier needs them.
- **Issuance.** Proposed: import only in 1.4; OpenID4VCI (a wallet-initiated issuance flow) later.
- **Encrypted responses.** Whether 1.4 implements `dc_api.jwt` (ECDH-ES to the verifier's key) or refuses such requests.
- **Where approval lives.** Proposed: the CLI and its event stream. An owner approving from their own Ghostly app, through a chat with the bot, would be a later profile of [406](406-message-buttons.md).

## Conformance

Before Proposed: unit tests of the parsing module against the specification's examples (Appendix A) and its request schema, with each refusal (version, scheme, duplicate header, oversize, bad base64url, expired, wrong host, bad signature); SD-JWT VC presentation tests (only approved disclosures, Key Binding JWT fields); grant matching (subset yes, superset no, unsigned no); and an end-to-end test of `ghostly x401 fetch` against a local verifier built from the specification's examples, with test credentials from a test issuer. No real identity document is used in tests.
