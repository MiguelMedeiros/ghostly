The Desktop sandbox spike measured the runner on WKWebView (macOS 15.6) with a malicious app in an `app-*` window on the `ghostly-app` scheme, against local listeners and a control with no policy. The CSP `sandbox` header from a Tauri custom scheme is honoured (origin `"null"`, no storage, no service worker); fetch, XHR, images, CSS, fonts, scripts, frames, media, forms, WebSocket, EventSource, `sendBeacon`, workers, `import()` and `<a ping>` reach nothing; `app_broker` reaches Rust through Tauri's `postMessage` fallback and knows the app by its window label, and every other command and plugin is refused there; top navigation, reloads, `window.open` and `target=_blank` are stopped by `on_navigation` and the sandbox. Two channels were open under the policy and are now closed: `<link rel=preconnect>` opened a connection, and a `srcdoc` frame had its own `RTCPeerConnection` and reached STUN and TURN, so the text no longer says the opaque origin protects nested frames. On Desktop `on_navigation` now refuses `about:srcdoc` and `about:blank` frames. The owner made the public layers required on Desktop (the CSP header, the navigation lock, and on macOS a content rule list that blocks every load but `ghostly-app:`), and WebKit's private preconnect, DNS prefetch, prefetch and WebRTC switches best-effort defence in depth: a missing key is logged and the window opens anyway. A per-window proxy was measured and does nothing in WKWebView. The threats table gains a residual: Tauri's IPC object is injected into app pages, so the capability and `only_main` are the only gates until the Desktop pull request keeps it out or says why it cannot. On WebKitGTK (Linux) the same run found the same results: the header honoured, every channel closed but `<link rel=preconnect>`, which connected under the header and the navigation lock; Linux app windows now get the same rule list as a WebKitGTK user content filter, required and in place before the broker hands over the entry, and `WebKitSettings` with DNS prefetch and WebRTC off, best effort. Measured again with the filter (WebKitGTK 2.52.6): `<link rel=preconnect>` reaches nothing under the full guard or the filter alone. That build has no WebRTC even when switched on, like Ubuntu's, Debian's and Fedora's, so on Linux nested-frame WebRTC is closed by absence, and on a WebKitGTK with WebRTC it would rest on the navigation lock and `enable-webrtc` off, unproven and listed as a residual. WebView2 and nested frames on the web are still to be measured.
