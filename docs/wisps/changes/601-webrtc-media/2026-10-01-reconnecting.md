Reconnecting: a connected call whose path is lost (a network change) now restarts ICE on its own connection instead of ending. New on the wire, all optional: `x: 1` on an offer or an answer (this side restarts ICE), the signal kind `r` (a restart offer: an offer's fields with new ICE credentials and candidates, the same fingerprint), and `re` on the answer to it (that offer's `ts`). Only the side whose offer was answered sends `r`: at once on a failed ICE or when the browser is online again, 3 s after `disconnected`, again every 8 s while the path is lost. Both windows say "Reconnecting..." and the call ends as before when no path is back in 30 s. Tracks, mute, devices and the clock stay, since the connection is the same. An app before 1.0.2 drops `r` (an unknown `t`), ignores `x` and never says it, so a call with it ends on a failed connection exactly as before. The web app, the extension and Desktop do this, the Linux native media too (ICE restarts in Rust, on sockets bound again). The headless CLI does not: libdatachannel cannot restart ICE on a started connection, so it never says `x`.
