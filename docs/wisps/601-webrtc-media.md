## Concrete signaling and media

The implemented 1:1 profile uses compact `_call` signaling and live `call` control frames, with ICE/fingerprint/candidate validation and a freshness window. Its v2 behavior pre-negotiates video so camera/screen changes can use `replaceTrack`; picture state is signaled separately. [Call signal validation](../../packages/core/src/callSignal.ts) and [the protocol](../PROTOCOL.md) define exact fields and legacy compatibility.

WebRTC is the media path. Voice, camera and screen permission must remain separate user choices; neither an invite nor a negotiated chat capability starts capture. End/hangup must stop capture tracks and release resources. Report permission denial or unavailable capture on the actual browser/native runtime.

## Paired profile

In the chat session ([401](401-paired-chat.md#calls-and-shared-apps)) calls are on while both sides offer `calls/1` on the live session.

Signaling: each compact signal above (offer `o`, answer `a`, hang-up `h`, picture state `v`: the JSON a compatibility chat keeps in `_call`) travels as `{"t":"paired-call","s":"<signal>"}` on the session, at most 8,192 characters. The receiver validates it as it would a `_call` record (anchored patterns, candidates re-serialized from their parts) and drops anything else, and drops every `paired-call` frame unless both sides offer `calls/1`. Nothing about a call is published on the DHT in this profile. **Time.** A signal's `ts` is its sender's clock: it orders that sender's signals, and settles two calls made at once the same way on both sides. It does not say how long ago the signal was made, nor whether it came before or after something the receiver did: two devices' clocks are often minutes apart. A signal on the session is heard when its frame comes, and the 120 second freshness window (an offer nobody answered stops ringing, a signal kept for a page that opens later goes stale) runs on the receiver's clock from then. An answer names the offer it answers by that offer's `ts`, and the caller takes an answer for the offer it names and no other: `o` names a call's offer, `re` names a restart offer (Reconnecting, below), and an answer carries one of the two, never both. A restart offer and its answer are heard like any signal on the session, so a contact whose clock is off reconnects as well; an answer that names none (an app up to 1.0.2) is taken when it was heard after the caller's offer went out. A signal read from a `_call` record, with nothing to say when it came, is still judged by its `ts` against the receiver's clock. A signal dated more than ten minutes ahead of the receiver's clock is not taken, however it came: a receiver acts on a signal only when its `ts` is later than the last one it acted on, and a time far ahead would outrank everything its sender says afterwards. An app sends its latest signal again on each new session while it is fresh; the receiving engine hands on only a signal newer than the last one it heard from that contact, so one already heard is not acted on twice (an answer that names no offer would otherwise be taken for a call placed since). (Until 1.0.2 every signal was: a call from a contact whose clock was two minutes off never rang, and the answer of a callee whose clock was behind by longer than it took to answer was dated "before the offer" and dropped, so the call rang on until it gave up. Such an app still does this to what it receives.) A signal on the session carries up to eight candidates (a `_call` record keeps one host and one server reflexive, a DHT packet's worth): host candidates on local networks first, then the server reflexive one and relay ones, IPv6, and last the host candidates a browser marks as costly (a VPN tunnel). A computer often has several interfaces, and the one listed first is not always one the contact can reach: on a Mac whose default route is a VPN, it is the tunnel's address, which nothing on that machine can answer. A call uses the STUN servers of the apps and then the profile's own ICE servers (Settings → Network), so a TURN relay set there carries the calls a direct path cannot: a VPN that takes every packet through its tunnel, or a NAT that maps each destination apart. The Linux Desktop's own call connection uses only the apps' STUN server so far, not the profile's ICE servers (`STUN` in `apps/desktop/src/native_call/engine.rs`). A signal that could not go (the session dropped between two frames) is sent again on the next ready session while it is still fresh; clearing it (after a hang-up) means there is nothing left to say.

Media: always a WebRTC peer connection of its own, separate from the session, whatever carries the chat (WebRTC, Iroh or HyperDHT). Iroh and HyperDHT carry the session's text frames, not RTP; the call's connection gathers its own ICE candidates (host, STUN and, with the profile's TURN relay, relay ones) and runs DTLS-SRTP end to end, as in a compatibility chat. The offer and answer carry that connection's DTLS fingerprint inside the authenticated session, so the media is bound to the contact the session authenticated, which a `_call` record read from the DHT does not give. A separate connection also means a transport switch of the chat does not interrupt a call.

**Offering again.** A caller whose connection did not come up may send one new offer, on a new connection (the headless CLI does when its WebRTC library refused a good answer, #403). An answerer that took a call whose connection never reached connected (ICE and DTLS) answers a second offer by starting over: it closes that connection and answers on a new one with the same microphone and camera, asking nothing again. When that connection fails first, it waits 8 s for such an offer before it ends the call, once: a failure after starting over is final. A call this side placed, or one whose connection came up, ignores offers as before (`RESTART_GRACE_MS` in `packages/react/src/useWebRTC.ts`, #407). An older answerer rings a second offer as a new call.

**Reconnecting.** A connected call whose path is lost (a network change: Wi-Fi to mobile data, a VPN going up) restarts ICE on the connection it has instead of ending. Each side says it can with `x: 1` on its offer or its answer, and a call reconnects only when both said it; otherwise it ends on a failed connection as before. The side whose offer was answered restarts: it makes an offer with new ICE credentials and the candidates of the network as it is now, on the same connection (`createOffer({ iceRestart: true })`), and sends it as a restart offer, `{"t":"r","ts":…,"u","p","f","s","m","c","ss","x":1}`: the fields of an offer, the same DTLS fingerprint. The other side applies it to the call's connection and answers with an ordinary answer that names the offer, `"re": <the restart offer's ts>`. Only one side ever sends `r`, so two restarts cannot cross; a restart offer that reaches the side that placed the call, a side with no call on, or one with another fingerprint than the call's, is dropped, and it never rings. The caller takes only the answer whose `re` is its latest restart offer. It restarts at once when ICE says `failed` and when the browser says it is online again, and 3 s after ICE says `disconnected` if the path has not come back by itself. While the path is still lost it restarts again every 8 s (the new network may not have been up when the last offer gathered), and an offer with no candidate at all is not sent. Both call windows say "Reconnecting..." in place of the clock. If no path is back 30 s after it was lost, the call ends as a failed connection ended it before, with its "call ended" line and its length. The connection is the same one throughout: its tracks, a mute, the chosen devices, a shared screen and the call's clock stay as they are. The signals travel like any other: one that the session could not carry (it often drops with the same network change) goes on the next ready session, and a compatibility chat polls faster while it reconnects. An app before 1.0.2 does not know `r` and drops it (its reader refuses an unknown `t`), ignores `x`, and never says `x` itself, so a call with it behaves exactly as before on both sides. The apps do this: the web app, the extension and Desktop, whose Linux native media restarts ICE in Rust (`ICE_DISCONNECT_GRACE_MS`, `RECONNECT_TIMEOUT_MS`, `ICE_RESTART_RETRY_MS` in `packages/react/src/useWebRTC.ts`). The headless CLI does not say `x`: its WebRTC library cannot restart ICE on a connection that has started, so a call with it ends on a lost path as before.

**Both call at once.** An offer that arrives while this side is calling (its own offer sent or still gathering) is glare. Both sides decide the same way from the two offers: the one with the earlier `ts` wins, and at the same millisecond the one whose DTLS fingerprint (`f`) sorts lower. An offer still gathering counts as later. The side whose offer lost drops its own attempt and releases its microphone and camera. It sends no hang-up, because that would end the winner's call, and it rings with the winner's offer like any incoming call. Its chat takes back the "call started" line of the attempt that lost, so both chats keep one call: the winner's lines only. The winner goes on calling. The apps do this: the web app, the extension and Desktop, whose Linux native media runs under the same call logic (`packages/react/src/useWebRTC.ts`; its Rust engine only makes the offer and answer it is asked for). The headless CLI does too (`packages/cli/src/calls/manager.ts`): its call that lost ends as `crossed`, and the contact's call rings as `call.incoming`.

**On a call already.** An app is on one call at a time. A call is on from the moment it is placed or answered (ringing out, answering, connecting, connected) until it ends. A call from another contact that rings while one is on rings as any call does (the chat's mute rules apply), with two choices: End and answer, and Decline. End and answer hangs up the call that is on as its person would: its contact gets the hang-up `h`, both chats keep its end line ("call ended" with its length, or "call cancelled" for a call still ringing out), and its microphone and camera are let go. Then the new call is answered as it came, with the camera for a video call. Decline declines it (the caller keeps a "call declined" line), and the call that is on goes on. The caller of the second call hears it ring as usual. When that caller hangs up while it rings, the ring stops with a "Missed call" line and the call that is on is untouched. When the call that is on ends by itself while the other rings, the choices are the usual Accept and Decline again. Two calls that ring with none on both offer Accept, and answering one turns the other's choices into End and answer and Decline. No call is placed while one is on: the other chats' call buttons are off and say why. A second offer from the contact already on the call is not a second call: it follows "Offering again" and "Both call at once" above. The apps do this: the web app, the extension and Desktop, whose Linux native media runs under the same call logic (`packages/react/src/callRegistry.ts`, `useWebRTC`). The headless CLI keeps a call per chat and reports each `call.incoming` to its program, which decides. No signal was added.

**Ringing.** An unanswered call rings for 60 s. The caller then hangs up (a hang-up `h`, as when the person cancels), says "No answer" and keeps a "Video call, no answer" (or audio) line in the chat. A side that rings sends nothing but a decline, so a hang-up that reaches a caller after its offer, while it rings, is a decline: the caller keeps a "Video call declined" line. A call the caller hangs up while it rings keeps a "Video call cancelled" line, and one ended while it still connects a "Video call ended" line with no length. The side it rang stops ringing on its own after 60 s from when the offer arrived, sends nothing, and keeps a "Missed call" line in the chat; so does a caller's hang-up that arrives while it rings. Each side times its own ring, so an older caller that never gives up still stops ringing here. The apps time both sides with `RING_MS` in `packages/react/src/useWebRTC.ts`. The headless CLI rings a call it places for the same 60 s (`RING_MS` in `packages/cli/src/calls/manager.ts`) and reports a call it was rung for as missed when the caller hangs up or the offer goes stale (120 s). No signal was added.

**Locked.** A call that rings while the app is locked (its lock screen, [04](04-profiles.md#security-and-privacy)) rings as it would unlocked: the same sound (a muted chat still rings), the same 60 s before "Missed call", the same "Both call at once" and "On a call already". The lock screen shows who calls, by the name and picture the chat shows (a nickname given there, the identity the contact is shown as, their own name and picture, else their key's pattern), and "Incoming audio call" or "Incoming video call", with Decline and Answer. Nothing else of the chat or of the app is shown, and the app stays out of reach under the lock. Decline declines as usual and the app stays locked. Answer asks for the lock password in the lock screen's own field; a right one unlocks and answers at once (with the camera for a video call, as "End and answer" does), and opens the call's chat. A wrong one is said under the field and the call keeps ringing; the lock's wait after repeated wrong passwords applies as usual. A call that stops ringing meanwhile (hung up, missed, answered or declined elsewhere) leaves the plain lock screen. On a call already, Answer reads "End and answer". The ring's system notification stays as private as unlocked: it names no one. An app locked since it started has drawn nothing yet, but its peer runs: a call that rings there loads its chat alone, only while it rings, and that chat draws nothing (no message, preview or name), only its call runs, so it rings, times out and declines as above. Answer then unlocks, puts the offer back for the chat the unlocked app opens, and that chat answers it at once (`PreUnlockRing`, `lib/lockedRing.ts`). A tab reloaded and not touched since may play no ring until it is clicked (the browser's rule for sound); the card still shows. The web app, the extension and Desktop share the lock screen (`apps/ui/src/components/LockScreen.tsx`, the chat registers its ringing call with `useRingOnLockScreen`). No signal was added.

**Couldn't connect.** A connection that has found no candidate at all after 4 s is made again, up to three in all, before its offer or answer goes out: a browser under load sometimes gathers none, and a description without a candidate can never connect. When none finds one, or when an answered call is still connecting 45 s after its answer, the call ends. The side that ends it hangs up with a reason, `{"t":"h","ts":…,"r":"u"}` (`u`: could not connect), and both sides keep a "Call couldn't connect" line in the chat. So does a call whose connection failed before it ever connected. A caller whose connections found no candidate sends nothing, because its offer never went out. `r` is optional, and a reader ignores any other value; an older app reads the hang-up as a plain one. The apps do this with `GATHER_STALL_MS`, `GATHER_ATTEMPTS` and `CONNECT_TIMEOUT_MS` in `packages/react/src/useWebRTC.ts`.

**Microphone or camera refused.** A call that cannot use the microphone or camera (the person, the browser or the system refused it, or there is none) says why and how to allow it. The caller's call ends before its offer goes out, and its chat keeps "Call couldn't connect" after "Call started". An answer that cannot use them hangs up with `r: "u"` instead of answering, so the caller stops ringing at once and both chats keep "Call couldn't connect". A camera refused when turned on mid-call says why, and the call goes on. The apps do this with `mediaProblem` in `packages/react/src/useWebRTC.ts`.

An app that cannot call does not offer `calls/1` and says why on its call buttons ("Calls are not available in this app", or its own reason); its contact's app says the contact cannot take calls. If the session drops during a call, the media goes on; the call ends on hang-up (sent on the next session while fresh) or when the media connection fails and does not come back (see "Reconnecting").

## Desktop on Linux

WebKitGTK, the WebView of Ghostly Desktop on Linux, is built without WebRTC by Ubuntu (22.04, 24.04), Debian 13 and Fedora 42: there is no `RTCPeerConnection`, and turning on WebKit's `enable-webrtc` setting changes nothing. So the Linux app runs the media connection itself, in Rust, and nothing on the wire changes: the same compact signals, the same WebRTC (ICE with STUN, DTLS-SRTP, Opus and VP8), so it calls browsers and other Desktops alike.

- **WebRTC** is `webrtc-rs`. Its host candidates end at `typ host` (browsers add `generation 0`), which a signal must still read as a host candidate; a socket on an unspecified address (`::` where there is no IPv6) gives no candidate. An ICE restart ("Reconnecting") binds its sockets again and gathers anew, so it finds the interfaces the machine has after a network change.
- **Media** is GStreamer: the microphone to Opus, the camera to VP8, and back through a jitter buffer to the speakers and to the page, which shows the peer's picture as JPEG frames drawn on a canvas. Only gst-plugins-base and gst-plugins-good are used; WebKitGTK depends on both, so an installed app has them. Not GStreamer's `webrtcbin`: its libnice links libsoup 2 on Ubuntu 22.04 and Debian 12, and loading libsoup 2 into a WebKitGTK 4.1 process (libsoup 3) aborts it.
- **Devices** are GStreamer's, known to the page by name: Settings lists them and the calls use the chosen ones. The page cannot hear that microphone or play on that speaker, so Settings' level meter reads GStreamer's `level` element on the chosen microphone, and its test sound is a one-second tone GStreamer plays on the chosen speaker.
- **Missing plugins**: the app checks for every element it uses when it starts. When one is missing it does not offer `calls/1`, and its call buttons name the packages to install.
- **Screen sharing** is not available on Linux yet (it needs the desktop portal): the share button stays in the call window, turned off, with that reason.

Permissions are the same choices: capture starts only when the person places or answers a call, or turns the camera on, and stops on hang-up.

## Headless Ghostly

The headless CLI ([1100](1100-headless.md#calls)) calls and answers in the chat session too, voice only, with its media in libdatachannel and Opus in WebAssembly, and hands the audio to a program. Nothing on the wire changes. Its offers have an audio section alone; it answers a contact's video section and drops what comes on it. Its signals carry up to eight candidates, every IPv4 host first (a server often has several interfaces), which a receiver already accepts. It does not reconnect a call whose path is lost: libdatachannel (0.24.5) refuses a remote offer with new ICE credentials on a connection that has started and cannot make one, so the CLI never says `x`, drops a restart offer, and its calls end on a lost path as before.

## Scope and evidence

This covers the calls of compatibility chats ([402](402-legacy-chat.md)) and of the chat session ([401](401-paired-chat.md)), in browsers and in the Linux Desktop's native media (`apps/desktop/src/native_call`, `apps/ui/src/desktop/nativeCalls.ts`). It does not add group calls, an SFU or an end-to-end encrypted forwarding-service claim. See [React call hooks](../../packages/react), [paired calls](../../packages/core/src/pairedCalls.ts). Exercise accept/reject/hangup, stale signals, simultaneous calls, denied permissions and camera/screen transitions on supported platforms, and in the chat session the live-only rule and a contact without `calls/1`.
