> This Draft documents a bounded existing profile, not full contract conformance or an independent implementation certification.

## Wire and authorization mapping

`ghostly-http/1` resolves an advertised service ID to a locally configured loopback target. The remote peer chooses a validated relative path, never an arbitrary host/port. The host's service configuration and selected contact audience are authoritative; advertisements cannot add targets or grant access. Current browser-engine `sharedWith` checks govern per-contact service advertisements/access; historical all-contact behavior is not the current policy.

Control `req` frames carry request ID, service ID, method, path, sanitized headers and body presence. `res` carries status/headers/body presence; bounded binary chunks carry bodies and `rst` cancels/resets. Reject unknown/disabled/unauthorized service IDs, invalid methods/headers, target escape, excess body/concurrency and idle timeout. Do not inherit the host's cookies or local credentials.

## Runtime limits

Desktop uses native local fetch, which reaches only the loopback addresses (scheme, host and port) the person allowed for that profile in a native dialog the app shows when an app is shared, or once on first use for an app shared before that list existed; the page can remove an address, never add one. Extension can host permitted local services. An ordinary web tab does not gain arbitrary loopback access. In compatibility chats ([402](402-legacy-chat.md)) these frames ride the legacy data link; in the chat session of every new chat ([401](401-paired-chat.md)) the same frames travel inside `ph` application frames ([pairedHttp.ts](../../packages/core/src/pairedHttp.ts)), under `services/1` ([below](#paired-profile)). Redirect containment differs across fetch implementations: browser follow-then-validate can observe a redirect only after it was followed. No WebSocket upgrade, SSE or end-to-end response-streaming support is implied by binary chunk framing.

## Paired profile

In the chat session ([401](401-paired-chat.md#calls-and-shared-services)) shared services are on while both sides offer `services/1` on the live session. The host tells the contact which apps it granted that contact with `{"t":"paired-services","s":<list>}`, the same list as `hello.svc`, once the contact said `services/1` and again whenever a grant changes; the list is never published. HTTP travels as `{"t":"ph","c":"<control frame>"}` (the `req`, `res` and `rst` frames above) and `{"t":"ph","b":"<chunk>"}` (a body chunk, base64url), since application data on this session is text on every transport. Both sides MUST drop `paired-services` and `ph` frames unless both offer `services/1` on this session, and a request made without a live session fails without reaching the host. The host checks the grant on every request, not only when listing: an app the contact was not granted answers 404 whatever it asks.

The web app shares nothing: a tab cannot reach a local address. It offers `services/1` only when it can open a contact's app ([On the web](#on-the-web)); a host then lists it what it granted, and any request the contact makes of it answers 404, since it grants nothing. Without that, a contact's app says so in the chat's Shared services dialog (composer +): "<contact>'s app cannot open or share apps". On the DHT the same dialog says "Shared services open while you are connected live".

## On the web

A contact's app is the contact's code: run on the web app's origin it could read the profile's keys and wallets. A web app built with a services host (`VITE_SERVICES_HOST`, `https://*.<domain>`, a wildcard name served by the same server) opens each one on an origin of its own, `https://<label>.<domain>`, where `<label>` is 32 z-base-32 characters of SHA-256 over `ghostly-web-service/1`, the `viewerTag` of this side's chat key ([04](04-profiles.md)), the contact's key and the service ID: another profile, or the same one made again, gets another origin and none of what the app stored. On those names the server serves only a bridge page and a service worker (`/_ghostly-svc/bridge.html`, `/ghostly-services-sw.js`), with `frame-ancestors` naming only the web app's own origin (`VITE_SERVICES_APP_ORIGIN`). The web app frames the bridge full screen under its own bar (✕ and the app's name), in a sandbox without `allow-top-navigation`, `allow-modals` or `allow-downloads` and with no `fullscreen` in either frame's `allow` (the contact's app can neither cover that bar nor open the browser's own alert or prompt over it, and starts no download on this device, as Desktop refuses every one it asks for), and hands it a `MessagePort`; the bridge registers the worker and frames the app under it. Every request the app makes reaches the worker, which passes it over the bridge to the web app's page, which sends it on the chat's live session like any viewer and streams the answer back. The worker drops the app's `X-Frame-Options` and `frame-ancestors` and sets its own; the page keeps the app's cookies for as long as it is open (a worker sees none), sends them back by name, and the app's script cannot read them. Closing it, a reload and the profile locking end it with its requests and cookies. The services host SHOULD be a registrable domain of its own, not one the web app's origin is under, and SHOULD be on the Public Suffix List (its private section): otherwise the apps' names are same-site with each other, and a script of one app may set a cookie for the whole services domain (`Domain=<domain>`) that another app's script reads, whichever chat or profile opened it (no request carries it: the worker sees no cookie, and the page sends only the jar's). A page's script sees only the cookies whose path its URL is under, so the bridge cannot find each one: the server answers `/_ghostly-svc/clear-cookies` on those names with `Clear-Site-Data: "cookies"`, which drops every cookie of the services domain's site at every path, partitioned or not. Before it frames an app, when the browser takes a cookie for the whole services domain from it, the bridge asks for that clear, and frames the app only once it is done; so where the services host is not a public suffix, no app's own cookie outlives another app's opening. When it clears an app's origin it asks for it always. On a services host that is a public suffix that site is the app's origin alone, and a cookie of the app's own origin stays until the clear. Two apps open at once can still share one there. A build without a services host, or a browser without service workers, offers no `services/1` and says opening needs the extension or the desktop app.

The frames around a contact's app (the view's and the bridge's) allow no `clipboard-write`, and that alone does not cover `document.execCommand("copy")`, which a browser lets write the clipboard for seconds after any tap in the page, from a timer too. So the web app puts a clipboard guard ([clipboardGuard.ts](../../packages/core/src/clipboardGuard.ts)) first in each HTML page of the app it passes on, and runs it in the bridge: `copy` and `cut` work only while one of the person's own inputs in that page is being dispatched (a trusted `pointerdown`, `pointerup`, `mousedown`, `mouseup`, `click`, `auxclick`, `dblclick`, `contextmenu`, `touchstart`, `touchend`, `keydown`, `keypress` or `keyup`, which no script can fire), or a trusted `submit` or `change` that starts before the first callback the guard queues at any such input has run (a message, a `user-blocking` task, an animation frame), and `paste` never. That window holds the input's default action (the submit of a click on a submit button or of Enter in a field, a checkbox's change), and also the rendering step right after the input: the animation frame callbacks the app asked for before the input run in the frame right after it, ahead of the guard's message and task, so a `submit` or `change` one of them fires counts (the guard's own frame callback closes the window there). A `submit` or `change` the app's script fires itself (`requestSubmit()`, `click()`) outside an input, or from a timer, a promise, a message or an animation frame it asks for at or after one, does not count. A copy button, a form, a checkbox, a double click or the app's own context menu still copies on the person's tap; nothing else writes the clipboard, so the app cannot swap what the person copied in Ghostly for text of its own. To put it there the web app rewrites the app's answer as it does for Hide my IP from contacts ([100](100-transports.md#relay-only-revision-2026-10-18)): the guard goes after the doctype, the app's own `Content-Security-Policy` takes the guard's hash where it would refuse an inline script, and a policy goes along that limits the app's frames to its own origin and refuses `javascript:` URLs (Trusted Types, with a default policy that passes every other string on, or to the app's own default policy: an app that makes one gets the guard's back, with its own rules in it); a page the guard cannot be put in runs no script. The guard also reaches the app's same-origin frames and the windows it makes there, as far as a script in the page can. The bridge looks at each page the app's frame loads, and a page of the app's (not an empty one, nor one that runs no script) in which the guard did not run, or that it cannot read (the app's own `sandbox` policy), is not shown.
